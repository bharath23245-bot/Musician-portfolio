1. EXECUTIVE SUMMARY & SYSTEM OVERVIEW
================================================================================
The Bharath Kannan Artist Platform is a production-grade, full-stack web application
engineered to solve two critical challenges for independent performing artists:

1. Public Conversion & Fan Engagement: Providing a luxury, audio-visual digital 
   presence featuring high-fidelity audio playback, tour calendars, artist biographies,
   and a frictionless booking proposal submission flow.

2. Centralized Business Management: Giving the artist a private, secured command
   dashboard to review incoming client proposals, schedule live concert dates,
   update brand photography on demand, and receive instant email alerts for new bookings.

2. IN-DEPTH TECHNOLOGY STACK BREAKDOWN
================================================================================

2.1 CLIENT-SIDE (FRONTEND ARCHITECTURE)
---------------------------------------
• React 18 (TypeScript):
  - Utilizes React's functional component paradigm and modern hooks (useState,
    useMemo, useEffect, useRef, useCallback, useContext).
  - Strongly typed with TypeScript strict mode, preventing runtime type coercion
    bugs and ensuring rigorous prop validation across components.
  - Implements Context API (AuthContext) for centralized authentication state
    management and session persistence.

• Tailwind CSS (v4 / Modern JIT Engine):
  - Tailored color palette: Deep Obsidian (#0b0c0e, #0e0f12), Muted Slate (#141518, #1f2128),
    and Classical Gold accents (#c8a251, #d6b25f, #e5c06e).
  - Responsive design using mobile-first utility classes (sm:, md:, lg:, xl:) ensuring
    seamless rendering across mobile phones, tablets, and ultra-wide desktop monitors.
  - Custom font hierarchy pairing serif editorial typography with clean modern sans-serif.

• Motion (motion/react):
  - Hardware-accelerated declarative animations for tab transitions, modal entrances,
    subtle hover ripples, and audio playback indicators.

• Lucide React:
  - Tree-shakeable, clean vector icons providing consistent visual cues throughout
    the UI (Music, Calendar, Mail, ShieldCheck, KeyRound, Bell, Settings).

2.2 SERVER-SIDE (BACKEND & API RELAY)
-------------------------------------
• Node.js & Express.js:
  - Custom server layer running on port 3000 that serves the client application in
    development via Vite middleware and in production via static asset streaming.
  - Houses backend API endpoints (/api/notifications/test, /api/health) to proxy
    and dispatch notification emails securely without exposing API keys to client browsers.

• Esbuild:
  - Bundles the backend server into a self-contained CommonJS artifact (dist/server.cjs)
    for high-speed production cold starts on cloud container infrastructure.

2.3 CLOUD PERSISTENCE & DATABASE (FIREBASE FIRESTORE)
---------------------------------------------------
• Google Cloud Firestore:
  - Scalable, serverless NoSQL document database.
  - Provides real-time query listeners and document snapshot capabilities for collections:
    * `admin_accounts`: Secure credentials and admin identities.
    * `bookings`: Incoming event proposals with status workflows.
    * `events`: Performance calendar items.
    * `profiles`: Dynamic artist biography, quotes, and photo URLs.

2.4 SECURITY & CRYPTOGRAPHIC SUBSYSTEM
--------------------------------------
• Web Crypto API (SubtleCrypto):
  - Standard browser-native cryptography engine executing non-blocking SHA-256 digests.
  - Incorporates deterministic application salts to prevent dictionary attacks and
    rainbow table matching against stored password hashes.

2.5 TOOLING & DEVELOPMENT ECOSYSTEM
-----------------------------------
• Vite: Next-generation frontend build tool with blazing-fast compilation.
• TypeScript Compiler (tsc): Zero-tolerance type validation with --noEmit.
• ESLint: Automated syntax and code quality verification.

================================================================================

PHASE 1: REQUIREMENTS ENGINEERING & ARCHITECTURE SCOPING
- Defined user personas: (1) Event Planners / Fans (Public), (2) Artist (Admin).

  and protected administrative controls.

- Crafted ergonomic component layouts: No cluttered nested cards, generous breathing room,

PHASE 3: COMPONENT ARCHITECTURE & MODULARIZATION
- Split application into isolated, single-responsibility components:
  * `App.tsx`: Root controller and route orchestration.
  * `PortfolioView.tsx`: Public presentation layer.
  * `AdminDashboard.tsx`: Comprehensive management interface.
  * `AdminLogin.tsx`: Secured authentication gateway.
  * `EventCalendarView.tsx`: Interactive concert calendar.
  * `AuthContext.tsx`: Authentication provider and state store.

PHASE 4: DATABASE MODELING & FIREBASE PROVISIONING
- Structured Firestore schemas for bookings, events, profiles, and admin accounts.
- Crafted robust security rules (`firestore.rules`) ensuring data isolation.

PHASE 5: CRYPTOGRAPHIC AUTHENTICATION ENGINE
- Implemented SHA-256 client-side hashing engine in `AuthContext.tsx`.
- Built account creation and verification pipelines interacting with Firestore.

PHASE 6: BOOKING PIPELINE & NOTIFICATION RELAY
- Connected the public booking form directly to Firestore.
- Added automated email notification alerts to notify the artist immediately.

PHASE 7: OPTIMIZATION & VERIFICATION
- Performed end-to-end linting, type validation, and production build checks.

4. DETAILED DATA FLOW & ARCHITECTURAL PATTERNS
================================================================================

4.1 CLIENT-TO-ADMIN BOOKING PROPOSAL LIFECYCLE:
  [Client on Portfolio] 
         │ 
         ▼ (Submits booking form)
  [Firestore `bookings` Collection] ──► [Automated Email Notification Relay]
         │                                            │
         ▼ (Real-time snapshot update)                ▼
  [Admin Dashboard Inquiries Table]          [Artist's Email Inbox]
         │
         ▼ (Admin marks 'Confirmed' / 'Declined')
  [Firestore Document Update]

4.2 ADMIN AUTHENTICATION LIFECYCLE:
  [Admin enters Email & Password]
         │
         ▼ (Web Crypto API SHA-256 + Salt)
  [32-Byte Hash String]
         │
         ▼ (Query Firestore `admin_accounts` where email == input)
  [Compare Password Hashes]
         │
    ┌────┴───────────────────────────┐
    ▼ (Match)                        ▼ (Mismatch)
  [Authorize Session & Set Cookie]  [Display Error Feedback]

5. DATABASE SCHEMA & COLLECTION STRUCTURE
================================================================================

1. Collection: `admin_accounts`
   - Document ID: Auto-generated / Email slug
   - Fields:
     * email: string (Normalized lowercase email)
     * name: string (Full Name / Display Name)
     * passwordHash: string (SHA-256 salted hash)
     * role: string ("admin" | "superadmin")
     * createdAt: timestamp (ISO 8601 string)
     * lastLogin: timestamp (ISO 8601 string)

2. Collection: `bookings`
   - Document ID: Unique UUID
   - Fields:
     * client: string (Client Name)
     * email: string (Contact Email)
     * phone: string (Contact Phone Number)
     * eventType: string (Concert, Gala, Wedding, etc.)
     * date: string (Event Date)
     * venue: string (Venue / Hall Name)
     * location: string (City, Country)
     * budget: string (Proposed Fee)
     * message: string (Event requirements)
     * status: string ("Pending" | "Confirmed" | "Declined")
     * createdAt: timestamp (ISO 8601 string)

3. Collection: `events`
   - Document ID: Unique UUID
   - Fields:
     * title: string (Concert / Tour Name)
     * month: string ("OCT", "NOV", etc.)
     * day: string ("24", "15", etc.)
     * fullDate: string (YYYY-MM-DD)
     * venue: string (Concert Hall)
     * location: string (City, Country)
     * ticketUrl: string (Direct ticket link)
     * status: string ("Upcoming" | "Sold Out" | "Completed")

6. SECURITY, DATA INTEGRITY & HARDENING
================================================================================
1. Zero Plaintext Passwords: Passwords never touch the database in raw text.
2. Input Sanitization: Form fields validate email formats, character constraints,
   and strip potentially dangerous HTML script tags.
3. Protected Routing: Unauthorized navigation attempts to the admin dashboard
   are automatically routed to the login portal.
4. Server-Side Secret Isolation: API keys and mail relay configurations remain
   isolated inside backend environment variables, inaccessible from browser tools.

7.2 STAR SCENARIOS FOR TECHNICAL INTERVIEWS:

• STAR SCENARIO 1: Cryptographic Authentication
  - Situation: We required a secure, persistent admin authentication mechanism
    without adding heavy third-party authentication dependencies.
  - Task: Implement client-side cryptographic hashing with Firestore validation.
  - Action: Utilized the native Web Crypto API (`crypto.subtle.digest`) with SHA-256
    and salt strings to hash credentials prior to Firestore querying.
  - Result: Lightweight, zero-dependency authentication with zero plaintext exposure.

• STAR SCENARIO 2: Real-time Cloud Synchronization & Optimistic UI
  - Situation: Admin updates to booking statuses or concert dates needed to feel
    instantaneous without lag.
  - Task: Combine responsive state management with persistent cloud storage.
  - Action: Architected optimistic state updates in React that update local state
    instantly while dispatching asynchronous writes to Firestore in the background.
  - Result: Zero UI stutter and sub-second feedback for administrators.
